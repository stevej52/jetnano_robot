# Visual odometry sweep, 2026-09-23

Overnight bench session on the Orin, robot parked on the tile floor, wall adapter, no
battery. Goal: the fastest visual odometry this hardware can give. Everything below is a
static-scene measurement; tracking under motion is the next job (the one-metre hand
slide of [bench-calibration-2026-09-21.md](bench-calibration-2026-09-21.md)).

## Conditions

- 01:47-04:00 the room was dark: colour image mean 6/255, and rtabmap's odometry had
  lost tracking (`quality=0`). Colour-based measurements waited for dawn; the rtabmap
  sweep ran 07:05-07:20 at a colour mean of 29-38/255, dim compared with the 2026-09-22
  daytime run, so its absolute numbers are a little worse than that day's (baseline 6.7 Hz
  here against ~10 Hz then). The comparisons between configurations hold.
- Camera 640x480x30 colour + aligned depth for rtabmap; the D435's infrared pair for
  cuVSLAM. Firmware 5.12.10.

## The infrared streams work

`sensors.launch.py` had them disabled with a comment saying the stock kernel's UVC driver
did not know the Y8 format. Re-tested with the camera node alone (`~/ir-test-2026-09-23/`):

| streams | result |
|---|---|
| infra1 + infra2 only, 640x360x60, projector off | 59.9 Hz each |
| infra1 + infra2 only, 848x480x60, projector off | 59.9 Hz each |
| infra1 + infra2 + depth + colour + aligned depth, 640x480x30, projector on, `enable_sync` | all five at 30 Hz |
| infra1 + infra2 + depth, 640x480x30 | 30 / 30 / 20 Hz |

`dmesg`'s "Unknown video format" lines are the RW16 and raw calibration GUIDs only. The
2026-09-22 stall was the camera left wedged by a driver crash; `initial_reset` clears it.
The launch-file comment is corrected; the streams stay off on the CPU path because
nothing there uses them.

## rtabmap `rgbd_odometry`: the CPU path (90 s each, `~/vo_sweep.sh`)

| config | parameters | `/vo` Hz | gap median / max ms | estimate ms | features / inliers | CPU (one core = 100 %) |
|---|---|---|---|---|---|---|
| A baseline | defaults (F2M) | 6.7 | 138 / 301 | 111 | 821 / 116 | 88 % |
| B | `Odom/Strategy 1`, `Vis/CorType 1`, `Odom/KeyFrameThr 0.6` (F2F, optical flow) | 12.1 | 70 / 249 | 46 | 990 / 892 | 85 % |
| C | B + `Odom/ImageDecimation 2` | 13.1 | 67 / 207 | 37 | 731 / 671 | 74 % |
| **D** | **B + `Vis/MaxFeatures 500`** | **18.7** | **42 / 173** | 28 | 499 / 467 | 79 % |
| E | B + both | 18.1 | 56 / 231 | - | - | 75 % |
| F | F2M + `Odom/ImageDecimation 2` | 6.9 | 135 / 308 | - | - | 86 % |

No tracking losses in any run. `realsense2_camera` (alignment + sync) took 39-46 % of a
core throughout.

Why the rate never scales with the CPU: the node has one worker thread and drops every
frame that arrives while it is busy, so the output is the camera rate divided by the
number of frame periods one estimate takes. That is also why MAXN_SUPER did nothing on
2026-09-21. Frame-to-frame with fewer features is the end of that road at ~19 Hz.
`odometry.launch.py` now carries config D as the CPU fallback; its drift under motion is
unmeasured.

## cuVSLAM: the GPU path (`ros2_gpu_robot/cuvslam_d435`)

Isaac ROS 4.6 Visual SLAM in stereo mode on the infrared pair, in NVIDIA's container,
publishing to `/vo` with `ekf.yaml` unchanged and the EKF still owning
`odom -> base_footprint`. 60 s each, `~/cuvslam_run.sh`:

| IR profile | projector | light | `/vo` Hz | gap median / max ms | cuVSLAM CPU | driver CPU | GPU | static drift 20 s |
|---|---|---|---|---|---|---|---|---|
| 640x360x60 | on (dot pattern, load only) | dark | 59.4 | 16.7 / 36 | 19 % | 21 % | 5 % | - |
| 848x480x60 | on | dark | 52.9 | 16.7 / 185 | 24 % | 27 % | 3 % | - |
| 640x360x90 | on | dark | 88.9 | 11.1 / 24 | 32 % | 31 % | 4 % | - |
| 640x360x60 | off | dawn, IR 42/255 | 59.4 | 16.7 / 35 | 23 % | 22 % | 5 % | 2.5 mm, 0.13 deg |
| **640x360x90** | **off** | dawn, IR 56/255 | **89.2** | **11.1 / 23** | 31 % | 29 % | 5 % | 3-6 mm, 0.30 deg |
| 848x480x60 | off | dawn | 55.8 | 16.7 / 100 | 26 % | 27 % | 6 % | 2 mm, 0.14 deg |

Soak: 640x360x90 with the projector on ran 04:00-07:00 at 90.0 Hz, cuVSLAM RSS 575 -> 585
MB, about 1 % of frames flagged for timing jitter, tracking state 1 throughout. System RAM
with cuVSLAM, lidar, IMU, EKF and tilt guard up: 1.8-2.0 GB used.

The 848x480 profile is not faster - the stream itself stalls (hundreds of "delta above
threshold" warnings and 100-185 ms gaps). 640x360 at 90 fps is the configuration to run.

## Decision

cuVSLAM stereo at 640x360x90: 89 Hz against rtabmap's best 19 Hz, on a third of the CPU
and 5 % of the GPU. The bench was left running it (container `isaac_vo`, `~/cuvslam.log`),
feeding the host EKF. rtabmap stays in `odometry.launch.py` as the fallback when the
container is not running.

Next: the hand slide with cuVSLAM (compare against rtabmap's 12 cm / 3.8 deg over 1.7 m),
then driving once the battery is here, then nvblox in the same container.
